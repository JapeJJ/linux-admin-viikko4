How server B was created

Before cloning, I switched server A's database from MySQL to MariaDB so that the replication follows the course material. Then I shut down server A with sudo poweroff so the database files were consistent, created a snapshot of it in cPouta and started A again. I launched server B from the snapshot (flavor standard.small), gave it its own floating IP and used the same security group. On B I disabled the week 2 app (systemctl disable --now viikko2) so it cannot write to the replica.

Hourly backup schedule

Server B pulls the backup from A (pull model), so even if A were compromised, it could not delete B's backups. User wwwbackup's crontab on B runs backup-www.sh every hour at minute 0 (0 * * * *) with flock to prevent overlapping runs. The script uses rsync over SSH through the internal network to copy A's /var/www/html into a new timestamped folder, e.g. /srv/backups/www/2026-11-22_1800. Each run writes OK or FAILED to /var/log/wwwbackup.log. The newest 48 versions are kept.

Continuous replication

Server A (primary, server_id = 1) writes every database change to its binary log. Server B (replica, server_id = 2) connects to A as user replicator through the internal network, reads the binary log and applies the same changes to its own database. I made the initial copy with mariadb-dump --master-data=2, imported it on B and started replication from the recorded binlog position. The dump files were deleted afterwards.

Why replication does not replace backups: replication copies every change within seconds, including mistakes. If a table is deleted or a wrong UPDATE is run on A, the same thing happens on B. Backups keep older versions, so data can be restored from before the mistake.

Test results

  • Both pages are public: A's /viikko2/ and B's /viikko4/ open from the internet.
  • A updates B: B's counter was 28. I loaded A's page 4 times and B's counter became 32.
  • B does not increment: the counter was 39, I loaded B's page 5 times and it stayed 39.
  • Replication status: SHOW REPLICA STATUS showed Slave_IO_Running: Yes, Slave_SQL_Running: Yes, no errors and Seconds_Behind_Master: 0.
  • Scheduled backups: automatic runs at 17:00:01 and 18:00:03 (UTC) both logged OK.
  • Restore test: I restored index.html from a backup to /tmp/restore-test. The sha256 checksum matched A's original: 8a250219ffa9bed2f75101ef6736db11cb4af4e233468f788a53f9b750208570
  • Reboot of B: after sudo reboot nginx, mariadb, viikko4 and cron were active, replication was Yes/Yes with 0 seconds behind, B's page showed new counter values from A, and the next scheduled backup at 19:00:03 UTC was logged OK.
